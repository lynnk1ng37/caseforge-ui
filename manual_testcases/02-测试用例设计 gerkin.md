# 模块 2：测试用例设计（120 条 · Gherkin / BDD）

> 目标：按 lilishop 买家端七个模块设计 120 条可执行场景，复杂模块（购物车、下单支付、个人中心/售后、会员资产）用例更多，首页与分销相对精简。
> 表达方式：全部用例使用 Gherkin（Given / When / Then / And），可直接导入 pytest-bdd、behave 或 Cucumber 系工具。
> 信息基线：官方文档（https://docs.pickmall.cn/help/distribution.html 及同站帮助中心）+ 本地部署（http://127.0.0.1/）的前端路由、页面文案与接口前缀。

## 2.0 编写约定

### 2.0.1 编号与标签

```text
LLS-模块缩写-序号
HOME  = 首页与搜索
GOODS = 商品详情与营销活动
CART  = 购物车
ORDER = 结算、下单与支付
UC    = 个人中心、订单履约与售后
ASSET = 会员资产与权益
DIST  = 分销中心
```

每个场景用标签标注优先级与类型，便于按标签筛选执行：

| 标签 | 含义 | 示例 |
|---|---|---|
| `@P0` / `@P1` / `@P2` | 优先级 | `@P0` 核心链路 |
| `@positive` | 正向：正常业务路径 | 正常加购、正常支付 |
| `@negative` | 负向：非法输入、不可用状态、失败路径 | 库存不足、券过期、未登录 |
| `@boundary` | 边界：阈值、长度、数量上下限 | 库存上限、门槛 M-0.01/M/M+0.01 |
| `@exception` | 异常：并发、篡改、网络、回调、缓存 | 并发核销、数量篡改、回调延迟 |

### 2.0.2 Gherkin 关键字约定

| 关键字 | 用途 | 写作要求 |
|---|---|---|
| `Feature` | 一个功能模块 | 用一句话说明这个模块解决什么问题 |
| `Scenario` | 一条独立用例 | 标题写“可执行的一句话”，必须带用例编号 |
| `Given` | 前置条件/初始状态 | 只描述状态，不描述操作 |
| `When` | 用户触发的操作 | 一条只做一件事，避免“打开页面并点击并提交” |
| `Then` | 可观察的预期结果 | 必须能被客观判定，禁止写“显示正常” |
| `And` | 延续上一个关键字 | 跟在 Given/When/Then 后补充同类步骤 |

**三条硬规则**：

1. 一个 `Scenario` 只验证一个业务结论，不把“登录 + 加购 + 下单 + 支付”塞进一个场景。
2. `Then` 必须断言用户可感知的结果（金额、状态文案、提示、订单状态），不能只断言 URL。
3. 数据细节用 `Examples` 表表达，避免写 10 个几乎相同的场景。

### 2.0.3 环境与数据基线

| 项 | 值 | 说明 |
|---|---|---|
| 买家 PC 端 | http://127.0.0.1/ | Vue 前端，接口前缀 `/api`【实测】 |
| 买家 H5 | http://127.0.0.1/h5 | 跨端一致性场景使用【实测】 |
| 客服 IM | http://127.0.0.1/im | 联系客服场景使用【实测】 |
| 接口前缀 | http://127.0.0.1/api | 抓包与接口篡改场景使用【实测】 |

| 库存 | 测试商品库存设为 5（可按场景调整） | 数量边界 |
| 优惠券 | 门槛 M、满减 A、店铺券/平台券各 1 张、1 张过期券 | 门槛/叠加/过期 |
| 礼品卡 | 2 张可用、1 张失效、1 张未激活 | 激活/抵扣/退款 |

> 标注约定：【实测】= 本次从本地部署前端资源或页面确认；【文档】= 官方帮助中心明确写出；【推演】= 依据电商通用规则推断，执行前需以实际配置确认。

### 2.0.4 前置条件里的“造数”是什么意思

指通过测试环境接口、数据库或 Mock 工具直接构造用户状态（库存、券、礼品卡、余额、积分、经验值、订单状态、分销关系），不通过 UI 一步步操作。企业里这是常规手段，面试时可以主动提，体现效率意识。

### 2.0.5 如何落地执行

- pytest-bdd：`pytest-bdd` 读取 `.feature` 文件，步骤文本与 `@given/@when/@then` 装饰器函数一一对应。
- behave：`behave features/`，按 `@P0`、`@boundary` 等标签筛选执行。
- 同一份 Gherkin 可同时给产品、开发、测试评审，评审通过后再补步骤实现，避免“用例写完没人看”。

```bash
# pytest-bdd 示例
pytest tests/features/ -m "P0" -v
# behave 示例
behave features/cart.feature --tags=@P0
```

> 注意：步骤文本一旦被自动化引用就相当于接口契约，改文案要同步改步骤定义，否则场景会变成“未实现步骤”。

## 2.1 Feature：首页与搜索（12 条）

```gherkin
Feature: 首页与搜索
  作为买家
  我希望在首页快速找到想买的商品，并在弱网或配置错误时仍能正常浏览
  以便以最短路径进入商品详情并完成购买

  @P1 @positive
  Scenario: LLS-HOME-001 未登录访问首页可浏览且登录入口可用
    Given 我已清除 Cookie 并使用无痕窗口
    When 我打开 http://127.0.0.1/
    Then 首页轮播、商品分类、楼层与推荐商品应正常展示
    And 顶部应展示“登录/注册”入口
    And 页面不应白屏、404 或出现接口 500

  @P1 @positive
  Scenario: LLS-HOME-002 顶部导航与分类入口跳转正确
    Given 我已登录买家账号
    When 我依次点击顶部“首页、商品分类、购物车、会员中心”
    And 我返回首页后点击任一一级分类及其二级分类
    Then 应分别进入首页、分类/商品列表、购物车、会员中心
    And 分类列表中的商品应属于所选类目
    And 页面标题和路由应与入口一致，无 404 或白屏

  @P1 @positive
  Scenario: LLS-HOME-003 首页楼层、轮播与推荐位跳转和参数正确
    Given 运营已在后台配置轮播、活动楼层与推荐商品且在售
    When 我依次点击轮播图、活动楼层和推荐商品
    Then 应进入与配置一致的落地页或商品详情
    And 商品详情 goodsId/skuId 应与推荐位配置一致
    And 不应出现错误链接、重复跳转或空白页

  @P0 @positive
  Scenario: LLS-HOME-004 有效关键字搜索命中商品并可进入详情
    Given 搜索服务正常且商品“测试耳机”在售
    When 我在搜索框输入“测试耳机”并提交
    And 我点击结果中第一条商品
    Then 结果应包含该商品且名称、图片、价格一致
    And 应进入对应商品详情页
    And 详情页 goodsId/skuId 与搜索结果一致

  @P1 @boundary
  Scenario Outline: LLS-HOME-005 搜索关键字为空、空格、1 字符与 50/51 字符边界
    Given 搜索框可用
    When 我输入 <关键字> 并触发搜索
    Then 应出现 <预期表现>
    And 页面不应白屏或返回 500

    Examples:
      | 关键字     | 预期表现                     |
      | 空值       | 提示“请输入关键字”或不发起请求 |
      | 纯空格     | 按空值处理                   |
      | a          | 返回匹配结果                 |
      | 50 个字符  | 返回结果或提示无匹配         |
      | 51 个字符  | 截断为 50 字符或提示输入上限  |

  @P1 @negative
  Scenario: LLS-HOME-006 无结果关键字展示空态且不残留旧结果
    Given 我已完成一次有结果的搜索
    When 我搜索“不存在的型号XYZ”
    And 我返回后搜索另一个关键字
    Then 应展示“暂无相关商品”空态与热门搜索/推荐
    And 不应残留上一次的搜索结果
    And 页面不应白屏或报错

  @P2 @negative
  Scenario: LLS-HOME-007 搜索特殊字符、XSS 与注入内容被安全处理
    Given 搜索框可用
    When 我依次输入 "<script>alert(1)</script>"、"' OR 1=1 --"、" %00 "
    And 我分别触发搜索
    Then 内容应被转义或拒绝
    And 不应弹窗、不应返回 SQL 错误或全量商品
    And 异常请求应被日志记录

  @P1 @positive
  Scenario: LLS-HOME-008 平台搜索与店铺内搜索切换后结果范围正确
    Given 我已进入某店铺页且该店铺没有商品“平台专供”
    When 我切换为“店铺内搜索”并搜索“平台专供”
    And 我切换为“平台搜索”并再次搜索“平台专供”
    Then 店铺内搜索不应返回其他店铺商品
    And 平台搜索应返回平台内匹配商品
    And 切换后关键字与结果范围应一致

  @P1 @boundary
  Scenario: LLS-HOME-009 列表筛选组合、非法价格与重置结果正确
    Given 商品列表支持品牌、价格区间、只看有货、新品、销量筛选
    When 我设置价格区间 0~0、最小值大于最大值、负数
    And 我组合品牌、只看有货与销量排序
    And 我点击“重置”
    Then 非法价格应提示或自动纠正
    And 结果商品应符合全部筛选条件
    And 重置后应恢复默认排序与全部品牌
    And 页面不应白屏

  @P1 @negative
  Scenario: LLS-HOME-010 秒杀、积分商城、优惠券入口在不可用状态下正确提示
    Given 首页已配置“限时秒杀、积分商城、优惠券”入口
    When 我分别点击三个入口
    And 我在活动未开始、已结束、已关闭时再次进入
    Then 进行中的活动应展示对应商品或券
    And 不可用活动应展示空态或“活动已结束/暂未开启”
    And 不应出现 404、白屏或错误价格

  @P1 @exception
  Scenario: LLS-HOME-011 弱网或首屏接口超时展示骨架屏并可重试
    Given 我将浏览器网络限制为 Slow 3G 或 Offline
    When 我打开首页
    And 我恢复网络后点击重试
    Then 首屏应先展示骨架屏或加载态
    And 超时应提示“网络异常，请重试”
    And 恢复后应加载成功且不白屏、不无限转圈

  @P2 @negative
  Scenario: LLS-HOME-012 楼层、轮播与商品图配置失效时页面正常降级
    Given 测试环境下线一个楼层、将一张轮播图替换为失效地址并配置一个下架商品
    When 我刷新首页并查看对应区域
    Then 空位应隐藏或展示默认占位图
    And 页面布局不应塌陷
    And 下架商品入口应隐藏或提示不可购买
    And 其他楼层应正常展示

```

## 2.2 Feature：商品详情与营销活动（16 条）

```gherkin
Feature: 商品详情与营销活动
  作为买家
  我希望在商品详情页选对规格、看清价格与活动资格
  以便按正确价格和数量购买，不踩限购、库存与活动坑

  @P0 @positive
  Scenario: LLS-GOODS-001 切换 SKU 后价格、库存、主图与 SKU 编号同步
    Given 商品有“黑色/白色”两个 SKU 且价格、库存不同
    When 我在详情页切换颜色
    Then 价格、库存、主图与 SKU 编号应同步变化
    And 不应出现 A 规格价格配 B 规格库存
    And 加入购物车时传入的 skuId 应与当前选择一致

  @P0 @positive
  Scenario: LLS-GOODS-002 商品基础信息、类型与价格展示正确
    Given 商品在售且已配置详情
    When 我打开商品详情页
    Then 应展示商品名称、价格、库存、规格、商品介绍、参数、评价、收藏/客服入口
    And 实物/虚拟/批发类型标识应正确
    And 价格单位与小数位应正确

  @P0 @negative
  Scenario: LLS-GOODS-003 下架、库存为 0 或活动结束时不可购买

    And 服务端不应接受超过库存或非整数数量

      | 数量 |

      | 6    |
      | 0    |
      | -1   |
      | 1.5  |
      | abc  |

    And 10 与 11 应允许且小计正确
    And 接口不应接受低于起批数量的请求

  @P0 @positive
  Scenario: LLS-GOODS-006 加入购物车与立即购买入口均可用
    Given 商品有库存且规格已选

    And 立即购买应进入确认订单页
    And 两处商品、规格、数量、价格应一致

    Given 商品参加店铺满减活动，门槛为 M、优惠为 A

    And 倒计时结束时间应与活动配置一致
    And 活动库存与商品库存应分别展示且不混淆

  @P0 @negative
  Scenario: LLS-GOODS-010 秒杀未开始、已结束或售罄时不可按秒杀价购买
    Given 秒杀活动未开始或已结束或已售罄
    When 我打开详情页并尝试购买
    Then 应展示“即将开始/活动已结束/已售罄”

    Given 本地版本已启用拼团活动且成团人数为 2、商品在活动期内

    And 同一账号重复参团应被拦截

  @P1 @exception
  Scenario: LLS-GOODS-012 拼团失败、超时与虚拟成团的退款和资产回滚
    Given 本地版本已启用拼团活动，并分别开启和未开启虚拟成团

    And 开启虚拟成团时应按规则成团或发货
    And 订单、库存、优惠券、礼品卡应回滚正确
    And 不应用户重复支付

  @P2 @positive
  Scenario: LLS-GOODS-013 砍价发起、帮砍一次与 0 元购买
    Given 本地版本已启用砍价活动、活动进行中且商品有库存

    And 我在积分不足时点击“积分购买”
    And 我在活动库存为 0 时点击“积分购买”
    Then 积分充足且有库存时应进入确认订单
    And 积分不足应提示并拦截
    And 库存为 0 应提示已售罄
    And 不应出现负数积分或超额兑换
```

### 2.8.3 为什么这样分配优先级

- **下单支付用例最多**：钱、库存、订单状态、券/礼品卡/积分/佣金都在这条链路上，出错就是资损或客诉。
- **个人中心与售后 20 条排第二**：订单状态、物流、售后流程与退款回滚是高频纠纷点。
- **购物车与会员资产各 18 条**：购物车是金额和库存的前端最后防线；会员资产覆盖券、积分、经验值、余额、礼品卡五类可被薅羊毛的资产。
- **商品详情 16 条**：规格、活动、限购、评价都集中在详情页，影响转化与活动公平性。
- **首页 12 条、分销 14 条**：首页主要是入口与体验，真正交易风险在下游；分销链路独立但资损风险高，因此 P0 集中在绑定、佣金、提现。

### 2.8.4 场景评审时的三个追问

1. **这条场景的 Then 能不能被客观判定？** 如果只能写“显示正常”，说明还没想清楚。
2. **这条场景失败时，能不能定位到前端、后端还是数据？** 不能定位的场景，执行价值低。
3. **这条场景有没有对应的接口或 DB 校验？** 纯 UI 断言容易被缓存和 Mock 欺骗。

## 2.10 面试怎么讲这套 Gherkin 用例

**问：为什么用 Gherkin 写用例？**

> “Gherkin 的价值不是好看，而是把‘前置条件、操作、预期’强制拆开，写的时候如果 Then 写不出可判定的结果，就说明用例还没想清楚。它还能直接给产品评审、给自动化复用：pytest-bdd 的步骤定义和场景文本一一对应，评审通过的场景不会在自动化里被改走样。我用标签区分 P0/P1/P2 和正向/负向/边界/异常，CI 里按 `@P0` 先跑冒烟，夜间跑全量。”

**问：Scenario 和 Scenario Outline 怎么选？**

> “一条场景只验证一个业务结论时用 Scenario；同一个逻辑只是数据不同，用 Scenario Outline 加 Examples，比如库存上限 5/6/999、地址手机号 10/11/12 位、优惠券门槛 M-0.01/M/M+0.01、经验值阈值 T-1/T/T+1。这样避免复制 10 条几乎一样的场景，改规则只改一处。”

**问：Then 里为什么经常出现具体金额和状态？**

> “因为用户感知的是金额和状态，不是 URL。只断言跳转成功，页面报价错了也会通过。所以购物车断总价、结算页断应付、订单页断状态文案和金额，必要时再补一层数据库终态校验。”

**问：lilishop 这套用例和普通电商用例最大的区别是什么？**

> “lilishop 是多店铺 B2B2C，多了平台券/店铺券、礼品卡、余额、积分商城和一级分销。普通电商只盯订单和优惠券，这里还要盯五本账：订单、库存、优惠、会员资产、分销佣金。尤其是分销佣金，未支付不计佣、支付后冻结、订单完成解冻、退款扣回，任何一个环节错都是资损。”

**问：如果时间只够跑 P0，你跑哪些？**
