# 转写清单规范

清单是「AI 提议 + 人确认」的唯一载体，落盘 `ui_test_dwp_temp/design_checklist.md`。

## 1. 三段结构

1. **页面与落点清单**：页面 → 路由 → Page Object → 新建/扩展/复用
2. **定位器清单**：元素 → 级别 → primary → fallbacks → 来源
3. **场景清单**：人工用例编号 → 场景 → 类型 → 前置数据 → 断言依据

## 2. 场景四维

| 类型 | 来源 | 示例 |
|---|---|---|
| 正向 | 人工用例主流程 | 加购成功、下单成功 |
| 负向 | 输入校验 / 业务规则 | 数量超库存、未选地址提交 |
| 边界 | 空态 / 极值 / 单条 | 购物车为空、列表只有 1 条 |
| 异常 | 登录态 / 权限 / 状态冲突 | 未登录访问订单页、已取消订单再支付 |

占比（场景数 ≥4 时机械校验）：正向 ≤50%、负向 ≥20%、边界 ≥15%、异常 ≥10%。

## 3. 字段要求

| 字段 | 要求 |
|---|---|
| 场景 | 中文业务语言，「谁在什么情况下期望什么」 |
| 类型 | 正向 / 负向 / 边界 / 异常，必填 |
| 人工用例编号 | 必填，保证可追溯 |
| 前置数据 | 写清来源：API 造数 / DB / 固定账号池 / 无 |
| 断言依据 | 具体元素+预期值，**禁止写「显示正常」** |
| 状态 | 待确认 / 已确认 / 已实现 / 待实现 / 已取消 |

## 4. 待确认规则

以下必须标 `【待确认】`，且**先提问再写代码**：

- 路由无法实测（页面 404 / 需要特定权限）
- 数据前置不可自造（如「待收货」需商家发货）
- 期望无法映射到可观测断言
- 文案/字段含义不明

## 5. 写完之后怎么回填（容易踩）

| 允许改 | 不允许改 |
|---|---|
| 场景清单最右侧「状态」列（待确认 → 已实现） | 场景 / 类型 / 前置数据 / 断言依据 的任何字面改动 |
| 「实现回填」表（位于确认小节之后） | 在确认小节之前新增或删除场景行 |

原因：指纹只覆盖「## 用户确认记录」之前的内容，并忽略表格末尾的状态列。
改了场景内容却不重新确认，G3 会报「确认无有效来源」——这是设计如此，不是 bug。
实现细节（用了哪个接口、造数方案、实测文案）写进「实现回填」的备注里。

## 6. 确认口令

| 用户回复 | 动作 |
|---|---|
| `确认，按照清单继续`（独立成行） | 改 `确认状态=已确认`，开始写代码 |
| 上面口令 + 其它说明行 | 同样算确认（口令必须自占一行） |
| 口令与说明写在同一行 | 不算确认 |
| `序号N，补充xxx` | 改清单，**改完必须重新确认** |
| 其它（含「继续」「写吧」） | 不算确认 |

> 结构约束：**场景必须写在「## 用户确认记录」小节之前**。
> 指纹只覆盖该小节之前的内容，写在末尾的场景不会让旧确认失效（回填表在末尾是设计如此）。

确认日志由 hook 落盘，AI 自行填写 `已确认` 会被 G3 识破。
