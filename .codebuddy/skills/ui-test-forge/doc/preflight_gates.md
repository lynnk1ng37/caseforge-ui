# 入口门禁（按任务类型分流）

## 1. 先判定任务类型

| 信号 | 类型 |
|---|---|
| 「把这批用例转自动化」「写 UI 用例」+ 人工用例文本/表格 | 转写 |
| 「用例挂了」「页面改版」「元素找不到了」 | 维护 |
| 「这条断言没意义」「用例是绿的但没验证」 | 断言加固 |

类型不明确时先问：**转写还是维护？**

## 2. 输入完整性检查（转写）

| 输入 | 必填 | 缺失处理 |
|---|---|---|
| 用例编号 / 优先级 | ✅ | 要求补，不猜 |
| 前置条件 | ✅ | 要求补 |
| 操作步骤 | ✅ | 要求补 |
| 期望结果 | ✅ | 要求补 |
| 环境地址 | ✅ | 读 `config.base_url_key` 环境变量，没有则问 |
| 可登录账号 | ✅ | 问；并确认能否走 API 登录 |
| 数据前置 | ✅ | 问是否允许管理端 API / DB 造数 |

**只给用例不够**：环境、账号、造数授权缺一个就进不了阶段 B。

## 3. 阶段 A / B / C

### 阶段 A：归一化

产出 `ui_test_dwp_temp/cases.yaml`，一条人工用例对应一条记录。
**只翻译，不补充**：人工用例没写的分支标 `【待确认】`，禁止发明场景。

### 阶段 B：可执行性尽调（五件事，缺一不可）

1. 环境可达：`base_url` 返回 200
2. 路由真实：用 `tools/probe_page.py --route` 实测，禁止猜
3. 登录态可得：优先 API 登录 → 注入 cookie（见 `mode_manual_convert.md` 第 2 节）
4. 数据前置可得：三级策略 ① API/管理端闭环 ② DB 直改 ③ 固定账号数据池
5. 期望可观测：每句「期望」都能映射到一个 `expect` / 业务断言

### 阶段 C：清单 + 确认

落盘 `ui_test_dwp_temp/design_checklist.md`，等用户回 `确认，按照清单继续`。
期间用户回 `序号N，补充xxx` 时，改完**必须重新确认**。
